# Agent Note: 打胶长度与挖矿深度拆分

Status: implemented

## Problem

原设计中挖矿是打胶的反向操作，两者共用一个长度，首次参与按 `18 ±45%` 初始化。用户要求两种玩法分开初始化：打胶默认 0 到 18 cm，挖矿默认 0 到 -18 cm，挖矿文案中的“长度”改为“深度”。

## Decision

- 用户确认采用两个独立数值：`impart_players` 的 `length` 与新增 `depth` 都是可空整数列（百分之一厘米），`null` 表示该玩法尚未初始化。打胶只读写长度，挖矿只读写深度。
- `initialVariance` 移除，改为长度与深度各自的下限、上限（`initialLengthMin/Max` 默认 0/18，`initialDepthMin/Max` 默认 -18/0），初值在区间内均匀随机；下限大于上限时 `Game` 构造即报错。用户要求上下限都可配置，不写死 0。生长系数仍在建档时生成一次并由两种玩法共用。
- 已有档案的玩家首次使用另一玩法时只初始化对应数值并消耗其冷却；初始化前只检查被初始化者的冷却，保持“帮助他人时先初始化目标、再初始化发起者”的顺序。
- 牛牛排行榜与仪表盘只统计已初始化长度的玩家，挖矿排行榜只统计已初始化深度的玩家并按深度升序。仪表盘名次按该群已初始化长度的参与者计算，群人数仍为历史参与人数。
- SQLite 驱动中字段默认可空，`length` 改为显式可空不改变列类型，不触发表重建；新增 `depth` 列以 `ALTER TABLE ADD` 加入，旧玩家长度保留、深度为空。

## Alternatives considered

- 仍共用一个数值，仅按首次指令决定初值正负：同一数值既称长度又称深度，与“初始化分开”的要求不一致，用户未采纳。
- 新增布尔初始化标记：需要额外默认值迁移，可空列已能表达同样状态。

## Consequences

挖矿不再影响长度，打胶也不再影响深度；旧版本中通过挖矿压低的长度保持原值。冷却仍为两种玩法共用。仪表盘只展示长度，不含深度。
