# Agent Note: 打胶与挖矿数据分开、共用冷却

Status: implemented

## Problem

长度与深度拆分后，生长系数、群参与记录仍由两种玩法共用，仪表盘也只展示长度：只挖过矿的玩家会计入本群打胶人数，挖矿沿用打胶时生成的系数。用户要求打胶与挖矿的数据各算各的，只共享冷却。

## Decision

- 用户确认三项都拆：生长系数、群参与记录、仪表盘展示。冷却 `lastActionAt` 保持一列，两种玩法共用。
- 生长系数：`growthFactor` 改为长度系数并允许为空，新增可空 `depthFactor` 作深度系数，各自在对应数值初始化时随机生成。宿主 SQLite 驱动遇到列改名（`legacy`）会重建整表，因此沿用 `growthFactor` 列名。
- 群参与记录：`impart_memberships` 新增 `length`、`depth` 布尔列（初值 `false`），打胶、挖矿分别标记；群榜与仪表盘按标记筛选。同一群同一玩家仍只有一行，群排序按该群全部参与人数。
- 仪表盘：总数改为打胶玩家、挖矿玩家、群组、进行中；每个群分别列长度（最长在前）和深度（最深在前）首尾各 5 名及参与人数。`Entry.length` 改名为 `value`。
- 迁移：`Game.migrate` 在插件启动时进入事务队列，幂等执行：已有深度且无深度系数的玩家复制旧系数；没有长度的玩家清空长度系数；两个标记都为 `false` 的旧参与记录按玩家已初始化的数值标记。

## Alternatives considered

- 参与记录按玩法拆成多行（主键含玩法）：需要删除并重建旧行，布尔列可直接 `ALTER TABLE ADD`。
- 旧玩家重新随机深度系数：会让已有深度的成长速度突变，用户选择沿用旧值。

## Consequences

旧参与记录无法得知玩家当时在该群玩的是哪种玩法，迁移按玩家当前已初始化的数值近似标记，可能让在别的群挖矿、本群只打胶的旧玩家出现在本群挖矿榜。空参与名单时直接返回空榜，因为 SQLite 驱动对空 id 列表的聚合查询会生成无效语句。
